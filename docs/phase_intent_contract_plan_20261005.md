后续用户将范围收窄为“重试的功能可以先不管，先把最核心的做好”。第一步的阶段生命周期与实现证据交接现已实施，见 [实际修复报告](intent_handoff_core_20261005.md)。下文涉及恢复重启的扩展未实施，第二步尚待具体规则确认。

## 已核对的实际调用链

- `loop._fresh_state` 构建新观测；`CapabilityRuntimeV1.probe_active_phase` 先调用 verifier 并处理阶段转换；`loop._attach_phase_feedback` 随后才附加局部意图上下文。
- `LocalIntentRuntimeV1.context` 在阶段 key 改变时直接清空执行记录；只要能力实例和最终目标没变，保留所选接近候选。选择接近候选时即写入该字段，并不要求已达到。
- 同一阶段中，点意图达到容差可标为 completed，但不完成能力阶段；这是应保留的正确边界。反过来，阶段通过时，未到达的点意图仍可保持 active，随后被清空而未明确结束。
- 两层动作输入对点意图裁掉阶段条件；对契约/接触意图保留阶段条件。所有动作输入都有文字 maintain，但没有统一的已核验约束状态。
- 现有阶段条件由 `PhaseConditionV1.satisfied` 计算三态结果。`PhaseDefinitionV1.maintain` 则是八类文字标识，包括持有、支撑、直到释放的放置关系、按压对齐和避开其他物体。两者不能一概升级为相同的硬拒绝规则。

## 第一步：显式结束意图，交接可核验的实现证据

### 职责

Runtime 继续依据原阶段契约推进；局部意图不能否决合法的阶段完成，也不能独立宣布阶段完成。阶段或能力结束、失败、恢复重启时，通用循环必须明确通知意图运行层，而不是等下一次 context 换 key 后静默删除记录。

### 意图结束语义

| 情况 | 局部记录 | 对阶段的影响 |
| --- | --- | --- |
| 点意图在新观测中到达，阶段条件尚未全部满足 | completed，允许选择同阶段其他意图 | 阶段仍由原 verifier 判断 |
| 阶段通过，点意图尚未达到 | superseded：因阶段完成而结束，不伪装成到达 | 保留合法阶段推进，不扣局部重规划预算 |
| 契约型意图由对应实际阶段契约确认完成 | completed，标明契约证据来源 | 不能用预测距离替代实际验收 |
| 阶段失败、能力切换或恢复重启 | cancelled，标明终止原因 | 沿用原阻塞/恢复机制，不复用旧命令绑定 |
| 同阶段观测变化、参考失效或无进展 | 仍采用原 invalidated 及预算语义 | 保留现有局部重规划机制 |

结束事件保留意图 ID、原能力与阶段、结束状态/动作 epoch/观测 ID、终止类别和原因。历史记录作为诊断数据保留，不能再充当活动意图。

### 跨阶段交接

分开表示“本阶段选中的计划”和“在新观测中核验到达的状态”。对当前唯一的接近侧面交接，继承的是“该预接触 XY 条件已达到”的证据，不是单纯的曾经选择，也不是物理接触证明。

证据记录主体、原能力/阶段、所选侧面与条件、核验状态/动作 epoch/观测 ID。交接时重新检查新鲜度、相同主体与能力绑定、当前几何及原参考变化阈值。几何未知、已经变化或只选未到达时，不限制下一阶段为该侧面；由 JEV 按新阶段状态重新选择，宿主不替它选另一侧。

当前阶段内完成接近后再调整高度的合法流程需要保留：高度调整前后的 XY 达到状态必须在交接观测中重新核验，不能仅依赖早先 completed 字样。

### 最小代码边界

- `contracts/local_intent.py`：增加明确结束状态及交接证据结构，历史执行与当前执行分开表达。
- `runtime/local_intent.py`：增加结束/交接入口；同阶段选择与跨阶段可核验状态分开管理。
- `runtime/loop.py`：在已有阶段转换、失败及恢复位置通知意图运行层并记录事件。阶段通过算法本身不因局部路线未完成而被加强。
- `policies/jev_context.py`、`policies/jev.py`：只把有效交接证据用于候选绑定；历史选择明确为历史，不能继续作为当前完成状态。

先建立契约结构，再逐个接入生命周期和实际循环。第一步不改 TaskPlan、阶段拓扑、场景、控制参数、验收容差或动作选择者。

### 第一阶段验收反例

1. 重放保存的 74.808 mm 交接：原合法阶段通过仍保留；旧点意图明确结束；未到达的侧面不能自动限制接触候选。
2. 到达所选点且观测有效：可形成带来源的交接证据；调整高度后 XY 偏离则撤销该证据。
3. 只选未执行、视觉过期、参考移动、主体切换、恢复重启：均不能继承为已达状态。
4. 抓取、按压、推动的点意图都能被阶段完成正常结束，不增加无效重规划次数；终止事件只产生一次。
5. 局部点目标已达到而阶段仍 pending：不能提前推进阶段。

先用契约和真实 Runtime 循环验证上述正反例；验证生命周期不依赖新任务成功率，也不需要先调用 JEV。通过后再进入第二步。

## 第二步：同一动作同时表达进展、完成条件和持续约束

将输入区分为三部分，复用现有条件比较器和阶段测量，避免再写一套不同的目标公式：

| 部分 | 回答的问题 | 能否独立证明阶段通过 |
| --- | --- | --- |
| 局部进展 | 当前所选意图的误差是否减少 | 不能 |
| 阶段完成条件 | 当前状态是否满足这一阶段的全部完成目标；动作名义预测会怎样改变可计算项 | 只有实际新观测和原 verifier 可以确认 |
| 持续约束 | 哪些关系声明要保持，当前是否满足、动作后是否能可靠预测 | 已知违反需明确反馈；未知不能标为满足 |

点意图动作输入也保留当前阶段的必要条件，但仍不发送其他局部候选或整个任务计划。已有支撑、持有、候选抓持等约束用公开测量归一化表达；“直到释放”采用明确的适用边界；当前缺少全路径检查的“避开其他物体”显式标为未验证，不伪造安全证明。

第一批动作预测只计算有公开几何支撑的 TCP 关系，如抓取/按压 XY、抓取高度带、推动 TCP 高度与外框距离。预测统一标为命令几何估计并注明固定目标等假设；接触、抓持、支撑及释放后的真实动态结果不能凭命令复制为 true。

现有接触高度仍先作为完成条件，给出预测变化，不因为一次失败就改成硬约束。可执行约束、未知处理与适用动作将在第一步验收后逐项核对，再确认第二步的审查规则。原阶段稳定观测逻辑不在预测中重跑。

第二步需要正反例同时验证：距离减少而某完成条件变差必须能看见；从未接触变为接触、从未持有变为持有不能被完成条件直接禁止；放置释放后的合法状态变化不能被旧维护条件误拒；未知接触/路径安全不得被预测为已成立。抓取、搬运、放置、推动、按压使用同一条件语义，分别核对其适用边界。
